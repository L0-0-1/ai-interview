# 并发（Day7 ~ Day11）

> 条目按学习顺序连续编号（1~12），回炉时直接按编号定位。

#### 1，线程的生命周期

- **NEW**：线程被创建
- **RUNNABLE**：包含了 ready（等分配到时间片就可以立马运行）和 running 两个状态，正在运行或者等待 CPU 分配
- **WAITING**：自己释放锁进入等待状态，等待其他线程唤醒
- **TIMED_WAITING**：有时间限制的等待
- **BLOCKED**：堵塞状态，等待锁被其他线程释放
- **TERMINATED**：终止状态，线程执行完毕消亡

![Java 线程状态变迁图](https://oss.javaguide.cn/github/javaguide/java/concurrent/640.png)

由上图可以看出：

- 线程创建之后它将处于 **NEW（新建）** 状态，调用 `start()` 方法后开始运行，线程这时候处于 **READY（可运行）** 状态。可运行状态的线程获得了 CPU 时间片后就处于 **RUNNING（运行）** 状态，时间片用完之后回到**READY**状态。

- 当线程执行 `wait()` 方法之后，线程进入 **WAITING（等待）** 状态。进入等待状态的线程需要依靠其他线程的通知才能够返回到运行状态。
- **TIMED_WAITING（超时等待）** 状态相当于在等待状态的基础上增加了超时限制，比如通过 `sleep（long millis）` 方法或 `wait（long millis）` 方法可以将线程置于 TIMED_WAITING 状态。当超时时间结束后，线程将会返回到 RUNNABLE 状态。
- 当线程进入 `synchronized` 方法/块或者调用 `wait` 后（被 `notify`）重新进入 `synchronized` 方法/块，但是锁被其它线程占有，这个时候线程就会进入 **BLOCKED（阻塞）** 状态。
- 线程在执行完了 `run()` 方法之后将会进入到 **TERMINATED（终止）** 状态。

#### 2，死锁的四个必要条件

互斥条件，持有并请求条件，不可剥夺条件，循环等待条件

#### 3，JMM（java memory model）java 内存模型

多线程并发的一种规范，规定了原子性，可见性，有序性

抽象了一个重要模型，共享变量放主内存区，每个线程存一个副本，线程先改自己的副本然后同步到主内存

#### 4，volatile

volatile 修饰的变量被修改后强制其他线程的该变量的副本失效，然后同步到主内存，其他线程想要只能重新取，由此实现了可见性

无法保证原子性，比如 total++ 实际上分为三步，当其他线程读到了旧数据，此时其他线程再改volatile变量，该线程还是会用已经读到的旧数据去改之后再写回去，只能用 synchronized 等方式保证原子性

#### 5，synchronized 和 volatile 的区别

synchronized 作用在代码块和方法上，开销较大，但是保证了可见性，原子性，有序性

volatile 作用在变量上，开销较小保证了有序性和可见性，无法保证原子性

#### 6，synchronized 底层原理

每个对象自带一个锁（monitor），synchronized 放在代码块上会用 monitorenter 先要锁才能进去，结束时用 monitorexit 释放锁，放在方法上则是标识当前方法是 ACC_SYNCHRONIZED 方法，需要锁才能调用，**底层都是通过 monitor 实现**，无论遇到异常还是正常执行都会释放锁

#### 7，锁升级

无锁 -（有一个线程进入）-> 偏向锁 -（出现竞争）-> 轻量锁 -（抢不到锁）-> 重量锁四个状态

jdk15默认关闭，jdk18 之后彻底废弃偏向锁，单线程就会直接进入轻量锁

#### 8，公平锁和不公平锁

公平锁需要按顺序排队来拿到锁

非公平锁允许插队（默认状态）新上来的锁可以直接插队拿到锁，这样可以少唤醒一次线程，减小了开销，效率更高

#### 9，synchronized 和 ReentrantLock 的区别

都是可重入锁，不公平锁

synchronized 会自动释放，属于 JVM 关键字

ReentrantLock 需要手动释放，属于 jdk 的 API，功能更多，可以设置锁的公平策略，设置等待时间即超时就放弃，获取锁可以被打断

#### 10，线程池提交任务后的处理流程

如果当前线程数 < 核心线程数就创建核心线程执行任务，否则放到等待队列**（因为创建销毁线程的消耗较大目前靠队列还可以撑住，当队列这层缓冲垫被冲破后才会创建非核心线程）**，当等待队列满了就创建非核心线程，创建之后第一个先去执行最新的任务，然后再去执行队列里的任务，如果等待队列满且线程数达到最大就会触发拒绝策略。

#### 11，为什么不能用 Executors 创建线程池

| 方法 | 坑在哪 |
| :--- | :--- |
| `newFixedThreadPool` / `newSingleThreadExecutor` | 队列是**无界**的（容量约 21 亿）→ 任务只进不出 → **OOM** |
| `newCachedThreadPool` / `newScheduledThreadPool` | 最大线程数**无上限** → 任务猛增就疯狂建线程 → **OOM** |

推荐自己new一个ThreadPoolExecutor（）显示指定七个参数

分别是：核心线程数，最大线程数，空闲线程等待时间，等待时间单位，等待队列，线程工厂，拒绝策略。

#### 12，execute 和 submit 提交任务

execute 如果遇到异常会抛出异常，如果没能在任务内处理就会直接终止当前线程

submit 在任务内部有兜底机制可以接住异常，异常被包住存到结果 future 里，该线程可以继续复用

#### 13，CAS（compare and swap）

CAS 即比较与交换，是实现乐观锁的一种方式。

写之前先比一下：现在内存里的值如果是刚刚读到的值就写，不是就不写（说明已经被别人改了）。

| 字母 | 是什么 |
|---|---|
| **V（var）** | 内存里**现在**的值 |
| **E（expected）** | 我**读到**的旧值（预期值） |
| **N（new）** | 我**要写**的新值 |

一句话规则：**V == E 才写 N**，否则放弃（或重试）。

它靠 native 方法把"比较"和"写"做成一个原子操作（底层是 CPU 的一条指令），所以不加锁也能保证原子性；而且失败的时候线程不会被挂起，重不重试我自己决定。

例：两个线程都读到 i=1、都想写 2。A 先改成功，B 比较时发现已经是 2，就不写，回去重读成 2 再写 3 —— 所以最后是 3，不是 2。

#### 14，CAS 的两个问题

**① ABA**：值是 1，被别人改成 2，又改回 1。我看到还是 1，以为没人动过，其实中间动过。
解决：给变量加版本号，值和版本一起比（AtomicStampedReference）。

**② 自旋开销大**：失败不挂起，就一直原地重试。成本不在"失败了几次"，而在**等待期间一直占着 CPU**，抢的人越多越亏。

| 等锁的方式 | 代价 | 什么时候吃亏 |
|---|---|---|
| 自旋（CAS 失败） | 一直占着 CPU 空转 | 抢的人多、抢得久（CPU 飙） |
| 挂起（抢不到锁） | 挂起/唤醒的切换开销 | 只差一瞬间就拿到时（切换不划算） |

`pause` 指令只是让空转便宜一点（少占 CPU、避免退出时清空流水线），它减少不了失败，也换不来更快成功。
真正的解法：限制自旋次数 / 自适应自旋，再抢不到就升级成重量级锁（这就是锁升级的场景）。

**③ 只能保证一个变量**：多个共享变量要包成一个对象，用 AtomicReference。

#### 15，ThreadLocal

作用：给每个线程存私有数据，线程之间互不影响。

原理：每个线程（Thread）里都有一个 ThreadLocalMap，是ThreadLocal的静态内部类，可以理解为local是对map的一种包装，ThreadLocal 是这个 map 的 key。线程的 map 不一样，所以同一个 key 在不同线程里取出来的值也不一样。

一般表示一类事物就用同一个local作为key，这样既节省了空间，每个线程用这个key得到的value也是自己私有的，各线程之间互不影响

```
Thread ──持有──> ThreadLocalMap ──Entry──> key   = ThreadLocal（弱引用）
                                    └────> value = 我的数据（强引用）
```

内存泄漏：key 是弱引用、value 是强引用。用完不 remove，key 被 GC 掉之后 value 还在 map 里，一直回收不掉。线程池的线程会复用、不会销毁，这些 value 就一直堆着；下一个任务还可能读到上一个任务留下的旧值（脏数据）。所以要在 finally 里 remove。
（补充：get/set 时会顺带清理 key 为 null 的格子，但只是顺手，不保证及时，所以还是得自己 remove。）

#### 16，AtomicInteger 原理（常考）

`getAndIncrement()` 就是"线程安全版的 i++"，靠 CAS，三步循环：

1. 读当前值 current（里面的 `value` 是 `volatile` 的，所以读到的一定是最新的）
2. `compareAndSet(current, current + 1)`
3. 成功就结束；失败说明被别人改过，**重新读最新值**再回到第 2 步（这就是自旋）

能安全靠三件事一起：CAS 保证"比较 + 写"不被切开，volatile 保证读到最新值，循环保证失败了还能再来一次。

> **我跑出来（5 个线程各加 500 次）**：`plain=2497  atomic=2500`
> 期望是 2500。`atomic` 一次没丢；`plain` 少了 3 次，就是 3 次"读—改—写"被打断（两个线程读到同一个值，各加 1 又写回同一个数）。
> 再跑几次 `plain` 每次都不一样（1972~2499 都可能）—— 所以这种丢更新的 bug 是**概率性**的，压测几次才复现，最难查。

#### 17，原子类 / 锁 / LongAdder 怎么选（常考）

判据只有一条：**冲突低还是高**。

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 冲突低（多读少写） | 原子类（CAS） | 不挂起、不加锁，一次就成功 |
| 冲突高（很多线程写同一个值） | `synchronized` / `ReentrantLock` | CAS 会大量失败重试、空转烧 CPU；锁让线程**排队**一个个来 |
| 计数热点极高 | `LongAdder` | base + `Cell[]` 把竞争拆散，各自 CAS，`sum()` 时汇总 |

注意锁的作用不是"防止多个写同时进行"，而是**冲突高的时候别让大家空转**。

`LongAdder` 是"空间换时间"：多占内存换掉自旋冲突，代价是 `sum()` 不是精确瞬时值。**这两句够用，面试问到的概率不高。**

#### 18，ConcurrentHashMap 为什么不允许 null（常考）

`get(key)` 返回 null 时有两种可能：**没有这个 key** / **有这个 key 但值是 null**，分不清 —— 这就是二义性。

- **HashMap 能容忍**：单线程下先 `containsKey` 再 `get`，两步之间没人能改，拼起来可信，二义性就消掉了。
- **CHM 不行**：两步之间别的线程能改：

```
T1: containsKey("a") → true     // 现在有
T2: remove("a")                 // 别人删了
T1: get("a") → null             // 值本来就是 null？还是刚被删了？
```

所以 CHM 干脆**禁止 null**，让 `get() == null` 唯一表示"没有这个 key"——**用限制换确定性**。

多线程里正确的做法不是"先查再改"，而是用原子的组合方法：`putIfAbsent` / `computeIfAbsent` / `compute`。

#### 19，HashMap 为什么线程不安全（常考）

`put` 是"读桶 → 判断空不空 → 写"三步，没有原子性。两个后果：

| 问题 | 怎么产生的 | 版本 |
|---|---|---|
| **数据覆盖** | 两个线程同时判断桶是空的，都往里写，**后写的把先写的盖掉**；`size` 也是各加各的，不准 | 1.7、1.8 都有 |
| **死循环** | 扩容用**头插法**，两个线程同时扩容同一个链表，**链表被翻转两次 → 自己指向自己形成环**，之后 `get` 掉进这个桶就出不来，**CPU 打满** | 只有 1.7 及以前 |

JDK 1.8 改成**尾插法**，环没有了，但**数据覆盖还在**，所以 1.8 的 HashMap 一样不能多线程写。

> 常追一句："1.8 修了死循环，是不是就能并发用了？" → 不能，覆盖没修，并发还是得用 CHM。

#### 20，ConcurrentHashMap 1.7 与 1.8 的区别（常考）

| | 1.7 | 1.8 |
|---|---|---|
| 结构 | `Segment` 数组 + `HashEntry` 数组 + 链表 | `Node` 数组 + 链表 / 红黑树 |
| 锁 | **Segment 分段锁**（`Segment` 继承 `ReentrantLock`），锁"一段" | **CAS + synchronized**，锁"一个桶的首节点" |
| 并发度 | 固定 = Segment 个数，默认 16，**初始化后不能改** | 不固定，不同桶可并行 |

一句话：**1.7 锁一段，1.8 锁一个桶，粒度更细。**
（常追：1.8 为什么换回 `synchronized`？JDK 1.6 后它优化过了，锁粒度又只到一个节点，开销可以接受，还省掉每个节点都挂一个 Lock 对象的内存。）

#### 21，CHM 1.8 的 put 怎么保证线程安全（常考）

就分两种情况：

| 桶的状态 | 怎么做 | 为什么 |
|---|---|---|
| **空桶** | `casTabAt` 一次 CAS 放进去，失败回循环重来 | 没人跟我抢，CAS 最便宜，不用锁 |
| **非空桶** | `synchronized (首节点)` 锁住，再分链表 / 红黑树遍历：key 相同就覆盖 value，不同就插到链尾 | 遍历 + 插入 + 可能转树是一串操作，CAS 保不住，只能上锁 |

- 锁的是**首节点**，所以同一个桶互斥、**不同桶并行** —— 这就是比 1.7 分段锁更细的地方。
- **读不加锁**：Node 的 `val`、`next` 和桶数组元素都是 `volatile`，写进去别人立刻看得见。

一句话答完：**空桶 CAS、非空桶锁首节点、读靠 volatile。**

（加分项一句带过：扩容时桶里放的是 `ForwardingNode`，别的线程碰到它会**帮忙一起扩容**。）

#### 22，AQS 的两个数字：state 和 waitStatus（常考）

**`state`** 是 AQS 自己的字段，`volatile int`，表示同步状态：

| 子类 | state 表示什么 |
|---|---|
| `ReentrantLock` | 0 = 没人持有；**2 = 同一个线程重入了 2 次** |
| `CountDownLatch` | 剩余待倒数的计数 |

**关键**：state 记的是"**资源被占用的次数**"，**不是排队人数**。两个线程抢锁时 state 只能是 0 或 1（拿到的人写的），抢不到的人进队列，不在 state 里体现。

**`waitStatus`** 是队列里**每个 Node 自己的状态**，跟 state 是两回事：`-1` = SIGNAL（该唤醒后继）、`1` = CANCELLED（已取消）、`0` = 还没设置。

一句话：**state 归 AQS 管（全局一个），waitStatus 归节点管（每个节点一个）。**

**重入是什么**：同一个线程已经持有锁，还能再拿同一把锁。因为 `a()` 里调 `b()`，两个方法都要同一把锁 —— 锁要是不认人，就把自己锁死在门外了。

锁认的是"**线程**"，不是"这一次调用"，所以 state 必须用**计数**：`lock` 1→2→3，`unlock` 减到 **0** 才算真释放。

> 换成 boolean 会坏两件事：
> ① 第二次 `lock` 看到 `true`，**分不清持有者是"自己"（该放行）还是"别人"（该拦住）**；
> ② **记不住层数** —— `lock` 两次只 `unlock` 一次，boolean 直接就变 `false`，锁被**提前放掉**，别人的临界区当场被击穿。

#### 23，AQS 抢不到锁 → 挂起 → 被唤醒（常考）

1. 抢不到 → 包成 `Node` **加到队尾**（CLH 双向队列，FIFO）
2. `acquireQueued` 里 for(;;)：**只有前驱是 head（轮到自己了）才 tryAcquire 抢一次**，抢不到就 `LockSupport.park()` **挂起**
3. 被唤醒后回循环再抢一次，抢到就把自己设成 head

> 每轮循环的顺序：**先看前驱是不是 head（是才 `tryAcquire`）→ 抢不到才去改 ws / park**。
> 改的是**前驱的** ws，不是自己的；改完当轮还不能睡（CAS 完返回 false），要再走一圈确认 ws 已是 -1 才真 park。

释放侧：`tryRelease` 先把 **state 减到 0**（重入过要减够次数），再 `unparkSuccessor` 唤醒 **head 的直接后继**（跳过 CANCELLED 的节点）。

> 顺序不能反：**先减 state，再唤醒**。反了的话被唤醒的线程跑来抢、state 还没减，白跑一趟。
>
> 反例（自测过）：A 重入 2 次（state=2），只 `unlock` 一次 → state 变 **1**，不等于 0 → `tryRelease` 返回 false → **B 不会被唤醒**，继续睡着。重入过几次就要解锁几次。

**队列六步**（A 持锁，B、C 来抢）：

```
state=1  队列空
B 抢失败 → 入队（先建一个占位 head），把 head 的 waitStatus 改 -1
B 试一次还失败 → park 挂起，状态 WAITING
C 抢失败 → 入队尾，把 B 的 waitStatus 改 -1；C 也 park
A unlock → state 变 0 → unparkSuccessor 叫醒 head 的后继 B，head 的 ws 改回 0
B 醒来再试一次 → 成功 → setHead(B)，老 head 出队；C 继续等
```

一句话：**state 管"锁到第几层"，waitStatus 管"要不要叫人"，prev/next 管"谁在我前面"。**
waitStatus **不是排队号，也不是优先级**，它只表示"我睡了，释放时记得叫我"。

#### 24，公平锁与非公平锁只差一行（常考）

```java
if (hasQueuedPredecessors()) return false;   // 公平锁 tryAcquire 里多这一句
```

非公平锁没这句，上来直接 CAS 抢 → 所以新来的线程能插队。

> 别把它和"前驱是不是 head"算成两句 —— `p == head` 在 `acquireQueued` 的循环里，**两种锁都有**（排队规矩是共用的）。公平锁真正多的只有入队前这一问。
> 而且这两句其实是**同一个判断的两种时机**：入队前问"队列里有没有比我早的"，入队后看"我前驱是不是 head"，都是在确认"**我是不是队首那个等待者**"。

**公平从哪来**：新来的线程必须先问一句"**有没有人在排队**"，有就老老实实去队尾，**没有插队的机会**；非公平锁不问，所以能插队。

精确说法：不是"队列为空才能抢"，是"**没有排在我前面的节点**才能抢"——队里只剩 head（我是第一个等待者）时照样能抢。
> 但在公平锁这个调用点上（**还没入队**），"队列非空"和"我前面有人"其实是**同一件事**，平时说"看队列里有没有人在等"完全够用；只有"队里只剩 head"这种边界才需要抠字眼。

> ⚠️ 别理解成"公平锁直接入队"：**队列空的时候公平锁也立刻抢到**，它同样先走 `tryAcquire`，只是多看一眼队列。差别只出现在"**已经有人在排队**"时：公平锁老老实实去队尾，非公平锁照样抢。

一次 `lock()` 里其实有**两次抢**，位置别搞混：
1. **入队之前**：`tryAcquire` 先试一下（公平锁在这步里多问 `hasQueuedPredecessors`，看到有人排队就**主动放弃这一抢**）
2. **入队之后**：`for(;;)` 循环里，只有**前驱是 head** 才再抢一次

所以公平锁不是"先入队"，是"**先抢，但看到有人排队就不抢了**"→ 才去队尾。抢不到的原因不同：非公平是被别人抢走，公平是自己放弃。

那"队列空时直接抢"算插队吗？**不算**。插队的定义是"**抢在已经在排队的人前面**"——队列空说明根本没人被抢。
所以公平锁保证的是这一句：**只要有一个线程在等，就绝不越过它。**

非公平的插队还有**第二处**：B 已经被唤醒了，但还没真正跑起来，新来的 C 抢先 CAS 把锁拿走 → B 白醒一次。抢得久了就是**饥饿**。


#### 25，CountDownLatch（常考）

就是个**倒计时牌**：构造时写 N，每个任务干完 `countDown()` 划掉一个，划到 0 时，卡在 `await()` 的线程才放行。`state` 就是还剩几次。

**谁等谁**：`await()` 随时可以调——`state` 不是 0 就一直阻塞在那儿，是 0 就立刻返回。`countDown()` 是任务端报数。所以是 **await 先堵在门口，减到 0 才开门**。

**和 join 的区别**（这才是考点）：

| | `join()` | `CountDownLatch` |
|---|---|---|
| 等什么 | 等**一个线程**结束 | 等 **N 次事件**，不一定是线程结束 |
| 数量关系 | 有几个线程就 join 几次 | N 和线程数**无关**：一个线程可以 countDown 多次 |
| 用起来 | 得先拿到每个 Thread 对象 | 只要共享一个 latch，任务之间互相不用知道 |

**一次性**：计数只能在构造时给一次，用完就废，想复用只能新建（或换 CyclicBarrier）。


#### 26，CyclicBarrier（常考）

**一句话**：N 个线程**互相等**，全部到齐才一起往下走；到齐之后**自动重置**，可以反复用。

两个比喻区分：
- CountDownLatch = **裁判等所有运动员跑完**（一个等 N 个）
- CyclicBarrier = **旅行团集合**，人齐才发车，下一站还要再集合一次

| | CountDownLatch | CyclicBarrier |
|---|---|---|
| 谁等谁 | 一个（或几个）线程等 N 个事件 | N 个线程**互相等** |
| 减到 0 之后 | 放行，**永久归零** | 放行并**重置回 parties**，进入下一代 |
| 能不能复用 | ❌ 一次性 | ✅ 可循环 |
| 底层靠什么 | AQS 共享模式 | ReentrantLock + Condition |


#### 27，Semaphore（常考）

**不是锁，是许可证计数器**：`state` = 还剩几个许可。
- `acquire()` 拿一个（state-1），拿不到（state=0）就进 AQS 队列挂起
- `release()` 还一个（state+1），唤醒等待的线程
- 多个线程能同时持有 → 属于 AQS **共享模式**

**和锁的区别**：锁是"一次只放一个"，Semaphore 是"一次最多放 N 个"。
**`Semaphore(1)` 退化成互斥锁**，但有一处不同：它**不可重入**——同一个线程再 acquire 会把自己卡死（唯一的许可已经被自己拿走了）。

典型用途：限流（连接池上限、接口并发上限）。


#### 28，Redis 五种类型怎么选（常考）

Redis 没有 int／对象，**存的都是字符串／字节**，类型只决定"这堆字节怎么组织"。

| 类型 | 对应 Java | 什么时候用 |
|---|---|---|
| **String** | 一个变量 | 缓存整个对象 JSON、计数器（`INCR`）、分布式锁 |
| **Hash** | `Map<key, Map<field, value>>` | 一个对象的多个字段，要**单独改某一个字段** |
| **List** | `LinkedList` | **有序**、只关心"最近 N 条"（`LPUSH` + `LTRIM`） |
| **Set** | `HashSet` | 去重、求交集（共同好友、点赞用户） |
| **ZSet** | 带分数的 `TreeSet` | 排行榜、按分数或时间排序 |

**"最近 20 条聊天记录"用 List 不用 Hash**：Hash 的 field 没有顺序、也没法自动淘汰最老的，取"最近 20 条"要全取出来在应用层自己排。List 一次 `LPUSH` 插头部 + `LTRIM 0 19` 就只剩 20 条。

**Set vs ZSet 的区别（容易混）**：

| | 元素能不能重复 | 有没有分数 |
|---|---|---|
| Set | ❌ 不能 | 没有分数 |
| **ZSet** | **member 不能重复**，**score 可以重复** | 有 |

所以排行榜里两个人战力**相同完全合法**——他们是两个不同的 member，score 撞了。score 相同时 Redis 按 member 的字典序排。
点赞用户用 Set：同一个人点两次自动只算一个，正好是我们要的去重。


#### 29，单线程的代价：一条慢命令卡住所有人（常考）

单线程 = **命令一条一条串行执行**。所以一条命令执行 2 秒，这 2 秒里**所有连接都在排队**，谁也进不来。

这**不矛盾**于"Redis 快"：快指的是**单条命令是纯内存操作、微秒级**。慢的是"用法错了"（`KEYS *` 扫全库、删几百万字段的大 Hash、超大集合求交集），不是 Redis 本身慢。

所以：生产**禁用 `KEYS *`**，用 `SCAN` 分批扫；Redis 4.0 加了大 key 异步删除；6.0 只给**网络读写**加了多线程，**命令执行仍然单线程**。


#### 30，什么时候多线程、什么时候单线程多路复用（常考）

判据只有一句：**一个线程处理一个请求的这段时间里，有没有大段"什么都不干"的空档？**

| | 空档多不多 | 用什么 | 例子 |
|---|---|---|---|
| 要等外部资源（DB、LLM、磁盘、网络） | **多**（线程干等着） | **多线程**，一个请求一个线程 | Tomcat |
| 纯内存操作，微秒级 | **几乎没有** | **单线程 + IO 多路复用**够用 | Redis |

**关键**：IO 多路复用只解决"一个线程怎么盯住几千个连接"，它**不会让一个慢请求变快**。所以慢任务照样得多线程——只是这时线程数要考虑到"大部分线程在等"，可以比 CPU 核数多很多。

**我项目里**：`ChatService` 调 LLM 要等 2 秒，属于"空档多"→ 该用多线程／响应式（项目里用的 `Flux` 就是这个思路）。**不是** Redis 那种场景。

#### 32，什么才值得缓存（常考，我答错了两处）

**错在哪**：① 我以为要缓存"聊天记录"——它不贵，缓存没意义；② 我跟着接受了"缓存 LLM 答案"——**这是伪需求**：用户问法千变万化，同一个问题几乎不会被问第二次，命中率极低，白加一层维护和不一致风险。

**四个指标，缺一个就不值得缓存**：

| 指标 | 说明 |
|---|---|
| 昂贵 | 一次几百 ms 以上 |
| **确定性** | 同输入必得同输出（LLM 带 temperature 就不完全确定） |
| **重复率** ← 最容易漏 | 这份产物**真的会被再要一次**吗 |
| 容错 | 短暂不一致能接受 |

**关键区分——重复从哪来**：
- ✅ **确定性重复**：只要这个输入在，就必须再算一遍 → 命中率接近 100%（语料 chunk 反复入库、批量任务重跑）
- ❌ **概率性重复**：指望用户碰巧问两遍 → 命中率极低

**我项目里真正成立的落点（B 类，还没做）**：
1. **embedding 缓存**（阶段 2 做 RAG）：文本→向量是**纯函数**，同文本必同向量。key = `emb:{模型}:{sha256(chunk)}`，调参数重跑入库时几乎全命中；文档只改 5% 就只重算 5%（**增量索引**）。
2. **限流计数**（阶段 4）：`INCR user:daily:{userId}:{date}` + `EXPIRE`。**这个压根不需要"重复"**，纯粹是高频率计数 + 控成本。

**key 设计原则（上面两个都适用）**：key 要包含所有"能影响结果的输入"，漏哪一维就在哪一维上串。embedding 缓存必须带**模型名**（换模型向量就变）；RAG 结果缓存要带**语料版本、topK、租户 id**。

**什么时候会让你答错**（针对 RAG 结果缓存）：

| 场景 | 后果 |
|---|---|
| 文档改了／删了，缓存还在 | 问已删除的内容，答的还是老的 |
| 模型升级、`temperature` 改了 | 命中老模型答的 |
| 问题一样但**用户不同**（"我的简历有什么问题"） | **答别人的** —— 最严重，是安全事故 |
| 需要实时数据（股价、时间） | 本身就是错的缓存对象 |

一句话：**先问"这份东西会被再要一次吗"，再问"key 漏了哪一维"。**
